# 通知设置运维化设计

## 目标

将单一的节点离线通知配置页整理为可操作、可验证的通知中心，保留 Telegram 和 SMTP 邮件，不增加 Webhook。

## 页面

页面按顺序展示三个区块：

1. **告警规则**：全局通知开关、离线阈值、事件选择（节点离线、节点恢复、节点版本过旧）与持续离线再次提醒间隔。
2. **通知渠道**：Telegram 和邮件各自显示“未配置 / 已配置未启用 / 已启用”的标签；开关使用有文字的控件，不再只在卡片角落显示无标签小开关。
3. **发送记录**：显示最新 100 条实际投递或测试投递记录，含时间、事件、节点、渠道、结果及失败原因；无记录时展示空状态。

表单只保存规则和渠道配置。测试按钮仍先保存当前表单再发送，以确保测试的是屏幕上正在编辑的配置。

## 数据与 API

`NotifyConfig` 新增：

- `notify_offline`：是否发送首次离线告警，旧配置缺失该字段时默认开启以保持原有行为。
- `notify_version_outdated`：是否发送节点版本过旧告警，默认关闭。
- `repeat_alert_minutes`：持续离线再次提醒间隔，`0` 表示关闭（默认，保持原有“只提醒一次”）。

每一次实际投递会写入 `notify:history:` 前缀的 KVS，保留最新 100 条。记录按渠道分别保存，因此 Telegram 成功、邮件失败会产生两条可诊断记录。新增管理员接口 `GET /admin/settings/notify/history` 返回最新记录。

## 监控行为

- 节点第一次越过离线阈值时，仅在 `notify_offline` 开启时发送离线告警。
- 节点恢复时，仅在 `notify_recovery` 开启时发送恢复通知。
- 持续离线仅在 `repeat_alert_minutes > 0` 且距离上次离线告警达到该间隔时再次发送；默认永不重复。
- 启用版本过旧后，监控器复用 30 分钟 GitHub Release 缓存，只有节点版本可解析且低于最新节点版本时发送一次；同一节点在同一目标版本下不会重复发送，新发布的目标版本会再次提示。
- 版本查询失败或节点版本缺失时不发告警，避免不可靠信息造成噪音。

## 错误处理与测试

- 通知失败不影响监控循环；失败详情保存到记录并提示在页面中。
- 表单继续阻止“已启用但未填写凭据”的渠道配置。
- 服务端测试覆盖：旧配置兼容、再次提醒时间判断、版本过旧判断、记录的排序与保留。
- 前端测试覆盖：三段布局、渠道状态、记录显示与空状态。
