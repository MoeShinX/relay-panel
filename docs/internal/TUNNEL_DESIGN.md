# 隧道转发设计（入口 ↔ 出口）

> 状态：**设计已定稿，未开始实现**。
> 决策人：浩哥。本文记录已拍板的决定和推导过程，避免实现时重新争论。

---

## 1. 要解决什么

国内入口机把流量转发到国外落地，**降低被 GFW 识别的概率**。

现有的转发是裸 TCP/UDP —— 用户客户端跑什么协议，出境这段在 GFW 眼里就是什么。
运营者对出境流量的样子**没有任何控制权**。隧道是为了把这个控制权拿回来。

### 非目标

- **不自研隧道协议。** 自研协议在对抗 GFW 上是负资产：只有本站用户在用的协议
  是流量里的"独角兽"，一旦被看一眼就是永久特征，而且没有社区帮忙跟进军备竞赛。
  更别说主动探测（GFW 连你的端口发垃圾数据，看回应像不像代理）这关，早期
  SS/VMess 就是死在这里。
- **不做 UDP**（第一版）。SOCKS5 的 UDP ASSOCIATE 实现混乱，各家不一致。
- **不改动现有转发。** 见 §3。

## 2. 历史包袱（先读这段）

这套东西**设计过两次、砍过两次**，数据模型的残骸还在：

- `device_groups.group_type` = `in` | `out`
- `forward_rules.device_group_out`（可空）
- `tunnel_profiles` 表（transport = ws | tls_simple）

**砍掉的真实原因**在 `crates/shared/src/protocol.rs`：

> chain is rejected (**node engine not implemented**)

面板侧的模型、API、UI 当年全做完了，**唯独节点侧的隧道引擎从来没写**。
后来 PR `10324f2` 干脆把 `forward_mode` 锁死为 `direct`，后端拒绝任何
`device_group_out`，免得用户配出一条不工作的规则。

**结论**：骨架可以复用，但缺的那一半（节点怎么把流量送到另一个节点）
依然是最重的部分 —— 这也正是本设计选择委托给 sing-box 而不是自研的原因。

## 3. 架构

```
客户端
  │
  ▼
入口节点 relay-node        ← 监听 rule.listen_port，计费在这里
  │  (本机回环)
  ▼
入口 sing-box              ← 面板下发配置
  │
  ▼  REALITY / Hysteria2 等，跨墙
  │
出口 sing-box              ← 面板下发配置
  │
  ▼
真实目标 (rule.target)
```

**关键性质:出口 relay-node 不在数据路径上。**

目标地址由隧道协议本身携带（VLESS 等都这么干），出口 sing-box 直接连目标即可。
出口的 relay-node 只承担**控制面**职责：接收并写入 sing-box 配置、上报健康状态。

这带来三个好处：

1. **重复计费问题不存在** —— 出口 relay-node 数不到任何字节，不需要任何
   "出口不要上报"的约定来兜底。
2. 出口机的转发性能不受 relay-node 影响。
3. 出口侧实现量小。

### 不影响现有转发

规则**不选出口分组** → 走现在的路径，代码一行不碰。
这也意味着可以灰度：先拿一条规则试，其它规则完全不受影响。

---

## 4. 计费语义

**完全不变。** 入口计数、入口分组倍率，就是现在的行为。

```
扣减额度 = (上行 + 下行) × 入口分组倍率
```

理由：好的入口（优质 BGP、低延迟）本身就该卖更贵，倍率挂在入口是对的。

必须保证的不变量：

- 计数发生在**内层数据流**上，不含 relay-node 到本机 sing-box 的 SOCKS5 握手字节
- 隧道不通导致连接失败 → 零字节 → 不扣额度
- 出口不上报这些规则的流量（由 §3 的架构天然保证，无需额外逻辑）

---

## 5. 隧道对象

新表 `tunnels`（不复用 `tunnel_profiles` —— 那张表的 tls_mode / ws_path / sni /
cert_id 对本场景基本用不上，塞进去会留一堆空字段）：

| 字段 | 说明 |
|---|---|
| `id` | |
| `name` | 显示名 |
| `group_in` | 入口分组 id |
| `group_out` | 出口分组 id |
| `protocol` | `vless_reality` / `hysteria2` / … |
| `listen_port` | 出口 sing-box 监听端口 |
| `config_json` | 协议参数（SNI、short_id 等），**不含私钥** |
| `secret_json` | 私钥等敏感材料，**只写不读** |
| `enabled` | |

规则侧复用已有的 `forward_rules.device_group_out`（当前被锁死，需解锁）。

**密钥材料只写不读** —— 和 `NotifyConfigPublic` 对 bot token / SMTP 密码的处理
一致：PUT 进去，GET 只回"是否已配置"，永不回传明文。

---

## 6. 面板下发配置

复用现有的 WS 控制通道，新增消息类型 `tunnel_config`：

1. 面板生成两端的 sing-box 配置（含密钥对，REALITY 需要 keypair + short_id）
2. 通过 WS 分别下发给入口和出口节点
3. 节点写入配置文件并重载 sing-box

**节点需要的新能力**（本设计最大的实现风险）：

- 管理 sing-box 进程（systemd unit 还是子进程？）
- 配置文件路径约定
- 重载机制（sing-box 支持热重载还是必须重启？重启会断连）

sing-box 由谁安装：建议**节点安装脚本顺带装**，避免用户手动步骤。

---

## 7. 失败处理：关闭，不降级 ⚠️

**入口的 sing-box 不可用时，必须拒绝该规则的连接，绝不回退直连。**

理由：一条本该走隧道的规则若悄悄改走直连，等于把明文流量直接发往境外 IP ——
恰恰是这个功能要避免的事，而且**运营者不会知道**。

要求：
- 连接被拒
- 规则上显式报错，节点状态页可见
- 日志明确写明原因

---

## 8. 版本门槛：拒绝下发，不静默忽略 ⚠️

新增规则字段意味着 `CONFIG_PROTOCOL_VERSION` 要升。

**老节点收到不认识的字段会忽略 → 直连转发 → 又是明文出境。**

所以：**面板必须在下发前拒绝**把隧道规则关联到不支持的节点，而不是发下去赌它。

参照 `node_supports_restart_rule` 的做法（硬 gate `>= 1.2.0`），但性质更严重 ——
那次是"功能静默失效"，这次是"静默降级到不安全状态"。

## 10. 分阶段

**阶段 0：手工验证链路**
不动代码，在国内节点手工装 sing-box + REALITY，确认延迟、速度、稳定性可接受。
沉没成本几乎为零；如果链路本身不成立，后面全不用做。

**阶段 1：隧道对象 + 生成配置**
面板存隧道元信息、生成两端配置供复制粘贴。验证配置正确性和计费口径。

**阶段 2：面板下发**
WS 下发 + 节点管理 sing-box 进程。这是工作量的大头。

---

## 11. 测试要求

- SOCKS5 握手成功/失败路径
- **隧道不通 → 连接被拒，且没有发生直连**（最关键的一条）
- **计费不变量**：计数 == 内层转发字节，不含握手
- 老节点关联隧道规则 → 面板拒绝，而非降级
- 密钥材料不出现在任何 GET 响应里
